# Byte encoding converter scoped verification

Demand is grounded in stored official LDDGO-02-013 (`base32-text`) and LDDGO-02-025 (`base58-data`) in `docs/research/2026-11-21-lddgo-full-comparison.json`. LDDGO Base32 declares configurable character sets/newline options; this tool implements UTF-8 and explicit ASCII whitespace removal only and does not claim those additional character sets. Base58 covers strings and raw files with Bitcoin alphabet, not arbitrary alphabet selection or Base58Check. Prior independent peer evidence is CyberChef official To/From Base58 operation research G50 in `docs/research/2026-11-20-global-tool-gaps.md`.

Original core API: `decodeByteEncoding(input, from, options)` returns exact bytes or a structured error; `encodeByteEncoding(bytes, to)` returns output text and byte count or error; `convertByteEncoding(input, from, to, options)` composes both. Encodings are `utf8`, `hex`, `base32`, `base58`, `base64`. Files enter as raw bytes and are never interpreted by extension or MIME. Normal decoding failures have no partial output.

Strict rules: HEX accepts either letter case but emits lowercase and requires complete byte pairs, without `0x`. Base32 uses uppercase RFC 4648 standard alphabet and canonical padding. Base64 uses standard `+/`, canonical padding and zero unused bits. Both are checked by canonical re-encoding. Base58 uses Bitcoin alphabet and preserves each leading zero byte as `1`; it is a byte representation, not the existing integer base converter. UTF-8 decoding is fatal, BOM is preserved, and text with unpaired UTF-16 surrogates is rejected before TextEncoder can replace them. No other text encodings, Base58Check or alphabet variants are promised.

Limits apply before large conversions: 262,144 UTF-16 input units before optional whitespace removal, 65,536 decoded/file bytes, and 1,024 represented bytes for Base58 input/output. The whitespace switch removes only ASCII HT/LF/VT/FF/CR/space from encoded input. It never trims UTF-8 text, removes Unicode whitespace, or guesses formats. Empty input is an explicit successful zero-byte value, with empty text/binary downloads available.

The file reader has its own request revision, separate from conversion-result revisions: a new file, source change, clear or unmount cancels stale file reads; a target encoding change invalidates only the old conversion result and preserves a pending valid binary read. Text edits, format or whitespace changes clear stale conversion results. Results disappear when source or options change; copy/download controls are only rendered for a successful current conversion. Downloads use real Blob content; binary downloads contain the original decoded bytes. Download exceptions produce a native error and never a saved confirmation. This is source and focused-test verification, not a browser acceptance or same-input peer test; root integration performs browser acceptance separately.
